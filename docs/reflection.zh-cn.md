# 设计思路

[English](reflection.md) · [DSL 规范 v1](spec.zh-cn.md) · [贡献指南](../contributing.zh-cn.md)

Timbrex 将台词、角色和表演指令放在同一份脚本中，便于与代码一起审查。主要设计取舍在于：语言需要承担多少职责，作者的意图如何映射到不同厂商，以及渲染器能保留哪些效果。

## 控制语言规模

纯文本就是合法脚本。点标签在台词附近插入事件或改变状态，span 将指令限定到特定文字。作者可以逐步增加控制，无需编写厂商请求体。结构语法使用英文 ASCII 标识符，台词和表演指令则可以使用任意语言。

代价是位置会影响含义：把 `[happy]` 从角色台词中移到独立一行，会将本轮指令变成场景状态。未来的格式化工具必须保留这个区别。隐式表演标签方便起草，也容易把拼写错误变成指令，因此长期维护的脚本适合使用严格模式和显式 `act`。语言仍可在开发过程中调整；修改这些规则时，需要用示例说明变化，并评估对现有脚本的影响。

## 区分作者意图与厂商实现

数值语速参数、SSML style 和自然语言指令都能表达表演要求，但精确程度不同。相同标签不会让不同厂商生成的声音自动一致。适配器需要说明如何表达请求，无法支持的控制应报错。将来若提供近似处理，也应让作者知情。

编译器将解析、词表检查和转换为 IR 分开。适配器接收结构化参数和完整 IR，无需重新解析脚本。这样既能让解析器独立于厂商规则，也允许适配器采用不同的渲染方式。一次合成只使用一个厂商；若厂商支持模型设置，该设置应用于整次合成。cast 映射在该厂商内选择音色。

## 保持有序渲染

共享规划器将场景、发言和 span 状态解析为片段。HTTP 适配器在网络 I/O 前准备所有片段的请求，因此即使不支持的控制出现在脚本末尾，也能在发送合成请求前报错。随后渲染器将格式兼容的 PCM 片段和本地静音拼成 WAV。

生成默认仍为串行。可选的[有界并发](providers.zh-cn.md#并发生成)让独立请求并行进行，同时由单一写入流程保持片段顺序。重排窗口与并发数绑定，前面的慢片段会形成背压，而不是在内存中保留整份脚本的音频。这会牺牲一部分潜在吞吐量，换取有界的音频保留量和较简单的失败清理，但不承诺真实提速幅度或可复现的声音效果。

这种方式便于检查和测试，但分次请求会增加延迟，片段之间也可能出现听感断裂。它不能混音、叠加声音或重采样，也不能保证片段衔接自然。厂商适配器能够访问完整 IR，后续可考虑利用原生 SSML 或行内控制保留整句，减少因控制变化而拆分片段。是否采用这种方式，应由实际测试结果决定。

## 说明验证能证明什么

`check` 判断脚本是否符合已实现的语言规则；厂商请求准备阶段判断所需控制能否映射为请求。未来若增加面向指定厂商的检查，可以在无需凭证和网络调用的情况下复用这段逻辑。

官方 API 文档为请求字段的选择提供依据。离线测试验证序列化、作用域恢复、错误处理、取消和输出保留，无法证明账号当前可用或音质合格；这些需要单独进行真实服务验证。[能力参考](capabilities.zh-cn.md) 记录当前适配器的行为。跨厂商声音一致性、情绪强度校准和声音输出可复现性仍有待解决。
