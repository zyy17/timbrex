# 设计思路

[English](reflection.md) · [教程](tutorial.zh-cn.md)

Timbrex 在一份脚本中记录台词、角色和表演。作者无需编写各厂商的请求体。

## 语言规模

纯文本无需配置。一种标签形式覆盖事件、状态和 span。`[whisper|Come closer.]` 将指令放在台词旁。`[pause 300ms]` 将停顿放在事件位置。解析器不把全角标点、圆括号或显示名称当作语法。明确规则使脚本可审查、错误可复现。

语法已冻结。新增能力通过词表或厂商映射实现。数据集循环和应用逻辑属于语音正文之外。格式化工具可以调整空白，不能发明含义。

## 意图与音频

标签表示作者的请求。适配器判断其 API 能否表达该请求。数值语速参数、SSML style 和自然语言指令是不同机制，不表示各厂商输出相同音频。

不支持的控制会失败，不会被丢弃。未来的降级必须暴露近似处理。能力表描述经过测试的适配器行为与模型限制，不是厂商宣传或未经验证的排名。

## 流水线

处理流程为 lexer → parser/AST → checker → lower/IR → provider。Lexer 处理文本与 token。checker 处理词表。provider 接收 IR。Cast 和配置成为 IR 字段。适配器不重新读取 YAML。带类型的参数在 lowering 时保持结构化。

Cobra 执行命令。`internal/config` 用 koanf 加载文件和环境变量。CLI 再应用脚本和参数覆盖。适配器接收解析后的选项。不使用全局配置单例。

规划阶段在网络 I/O 前解析场景、发言和嵌套 span 状态。各适配器在渲染前构造请求。共享渲染器拼接格式一致的 PCM 和本地静音，不进行混音、重叠或重采样。顺序调用会增加延迟，并可能造成听感不连续。这些限制应写在使用文档中。

## 证据

官方 API 参考为请求字段提供依据。离线测试覆盖请求体、作用域恢复、畸形响应、取消和输出保留。真实测试须另行验证账号兼容性和声音结果。文档须说明已有哪种证据。

中英文页面描述同一产品。示例必须能解析。命令必须存在。本地链接必须可解析。规划功能必须标为规划。

## 边界

按位置确定作用域具有语义：把 `[happy]` 移到独立一行，会从本轮指令变成场景状态。格式化工具必须保留这个区别。当前默认仍允许隐式自由表演指令。纳入版本管理的脚本应使用严格模式和显式 `act`。修改默认值需要明确的兼容性决策。

语言验证与合成支持是两个层次。`check` 确认语法和词表，适配器验证所请求的表演。未来面向指定厂商的检查，应在无需凭证或网络的情况下复用适配器的请求准备逻辑，而不是在 CLI 中复制能力规则。

共享片段规划器只是基础实现，不是厂商必须遵循的接口。适配器接收完整 IR，后续可以利用原生 SSML 或行内控制保留整句。不要在每个控制 span 处永久拆分。对能够表达整句的厂商，这会增加延迟、费用和听感断裂。

一次合成选择一个厂商和一个模型，cast 映射选择该厂商内的音色。跨厂商对话、经过校准的情绪强度、听感连续的片段边界和声音输出可复现性都不是当前保证。在增加更多词表或抽象前，应先通过实际测量建立这些保证。
