# 设计思路

[English](reflection.md)

Timbrex 的目的，是让富有表现力的语音易于编写和阅读。脚本应直接呈现台词、角色和表演方式，无需作者学习每家厂商的请求格式。

## 保持语言小巧

纯文本无需配置即可使用。一种标签形式覆盖事件、状态和 span。`[whisper|Come closer.]` 将指令与台词放在一起，`[pause 300ms]` 把停顿放在发生的位置。解析器不会猜测全角标点、圆括号或显示名称是不是语法。明确规则让脚本易于审查，让错误可以复现。

语法已经冻结。新增能力通常应通过词表或厂商映射实现。数据集循环和应用逻辑属于语音正文之外。未来的格式化工具可以美化源码，但不能替作者发明含义。

## 表达意图，不承诺相同音频

标签表达作者想要什么，适配器判断自己的 API 能否表达。数值语速参数、SSML style 和自然语言指令是不同机制，不能据此认为两个服务会产生相同听感。

当前实现对不支持的控制报错，不会静默丢弃。未来的降级系统必须暴露近似处理。能力声明应描述经过测试的适配器行为与模型限制，而不是厂商宣传或未经验证的质量排名。

## 让编译流程容易追踪

处理流程为 lexer → parser/AST → checker → lower/IR → provider。Lexer 只认识文本与 token，checker 认识词表，provider 接收 IR。Cast 和配置转为明确的 IR 字段，不让适配器重新读取 YAML。带类型的参数在 lowering 时保持结构化。

厂商规划阶段在网络 I/O 前解析场景、发言和嵌套 span 状态，各适配器在渲染前构造所有请求。小型共享渲染器拼接格式一致的 PCM 和本地静音，不试图成为通用音频工作站。顺序调用以部分连贯性和延迟为代价换取直观实现，这些限制应写在使用文档中。

## 让声明有据可查

官方 API 参考为请求字段提供依据。离线测试验证请求体、作用域恢复、畸形响应、取消和输出保留。真实测试需要另行验证账号兼容性和声音结果，文档应说明已有哪种证据。

中英文文档描述同一个产品。示例应能解析，命令应真实存在，本地链接应可解析，规划功能应明确标为规划。贡献规则和聚焦的 Conventional Commits 帮助审查者判断这些声明。

## 当前设计边界

按位置确定作用域很紧凑，但位置具有语义：把 `[happy]` 移到独立一行，会从本轮指令变成场景状态。格式化工具必须保留这个区别。当前默认仍允许隐式自由表演指令；对于纳入版本管理的脚本，建议使用严格模式和显式 `act`。修改默认值需要明确的兼容性决策。

语言验证与合成支持是两个层次。`check` 确认语法和词表，适配器验证所请求的表演。未来面向指定厂商的检查，应在无需凭证或网络的情况下复用适配器的请求准备逻辑，而不是在 CLI 中复制能力规则。

共享片段规划器只是基础实现，不是厂商必须遵循的接口。适配器接收完整 IR，后续可以利用原生 SSML 或行内控制保留整句。应保留这条路径：永久地在每个控制 span 处拆分，会给本来能够表达整句的厂商带来不必要的延迟、费用和听感断裂。

一次合成选择一个厂商和一个模型，cast 映射选择该厂商内的音色。跨厂商对话、经过校准的情绪强度、无缝片段衔接和声音输出可复现性都不是当前保证。在增加更多词表或抽象前，应先通过实际测量建立这些保证。
