# Timbrex 设计反思：怎样的 DSL 才真正"最易用 + 最可扩展"

> 2026-10-20。输入：`SPEC.md`(v0.2)、`SPEC.v0.1.md`、`CAPABILITIES.md`、`MARKET_SURVEY.md`。
> 结论先行：**v0.2 的能力模型与降级架构是对的，但表层语法和"语言边界"是错的**。v0.3 改成 "**一种括号、一条规则、一个开放注册表**"，控制流移出 DSL，语法冻结，所有增长都走词表与能力声明。最终设计见 `SPEC.v0.3.md`。

---

## 1. 第一性原理：这个语言到底给谁用、解决什么

| 事实 | 推论 |
|---|---|
| 大部分脚本将由 **LLM 生成**，人类做审阅和微调 | 语法要"LLM 已经会写"：贴近它见过最多的形态（ElevenLabs v3 `[tag]`、Markdown、剧本 `名字: 台词`）；规则少到能放进一段 system prompt；出错能被机器自动修复 |
| 人类作者以 **中文用户** 为主，用中文输入法 | 不能依赖 `<` `/` `\` `{` `@` `#` 这些在中文输入法下会变成 `《` `、` `、` `｛/「` 的字符；必须原生接受 `【】` `：` `｜` `“”` |
| 目标 provider 自己在用 `[]` `()` `<>` 三种括号，而且含义互相冲突 | DSL 自身只能**占用一种**括号，其余全部当普通文本，由编译器按 provider 转义 |
| provider 能力在快速变化（固定枚举 → 自由文本、新模态：唱、音效、实时） | 语法必须**冻结**，变化只能发生在"词表"（注册表）和"能力声明"（caps）两层；IR 必须是开放的 |
| 有三类本质不同的信息：**表演文本**、**配置**（音色/克隆/合规/输出）、**数据生成逻辑**（遍历/采样/切分） | 三者应各用最适合的载体，而不是塞进一种语法 |

"易用"的可操作定义：**作者需要记住的规则数 × 每条规则的例外数** 最小；"可扩展"的可操作定义：**加一个新能力时，需要改动的层越外越好**（理想：只加一个 YAML 文件，不改语法、不改核心、不改 IR 类型）。

## 2. 对 v0.2 的诚实批评

### 2.1 语法形态太多（真实计数：11 种）
`[点标签]`、`<区间>…</区间>`、`</>`、行首 `@指令`、`角色:`、`角色(情绪 强度):`、`> 旁白`、`#` 注释、`<!-- -->` 注释、`${}`/`$x` 插值、YAML front-matter，外加透传的第 4 条路（`[az:…]`、`<raw>`、`@param`、`@provider`）。
"只有三种标记"的说法不成立。每多一种形态，LLM 和人都要多记一条，且形态之间会互相干扰（`<sad 0.6>` 与 Gemini `<sigh>`、`>` 旁白与引用文本）。

### 2.2 同一语义多种写法
- 情绪：`[happy]`、`[emotion happy]`、`<happy>…</happy>`、`<emotion happy>`、`角色(happy):`、`[开心]`——6 种。
- 透传：`[el:…]`、`<raw azure>`、`@param el.x=`、`@provider`、YAML `per_provider`——5 种。
- 作用域：点标签状态的作用范围还要靠 `scope: sentence|turn|until-reset` 配置——**同一份脚本在不同配置下含义不同**，这是可读性的大忌。

### 2.3 `<…>` 是错误的选择
1. 与 SSML / Cartesia / Gemini `<sigh>` / CosyVoice `<strong>` / Fish `<emphasis>` 视觉同形，读者无法分辨"是 Timbrex 还是 provider 原生"。
2. 闭合标签要求名字匹配（`</开心>`），LLM 和人都常错；`</>` 又引入新规则。
3. 中文输入法下 `<` → `《`，`/` → `、`，写一个区间要切 3 次输入法。
4. 文本中数学/比较符号 `a<b` 需要转义。

### 2.4 `@指令` + 控制流把它变成了一门编程语言
`@for/@loop/@pick/@weighted/@rand/@if/@macro/@call/@include/@item/@provider` —— 这是"写在台词里的 Jinja"。示例 10.4 第 466 行：
```
${spk}: @if nv != "none" [${nv}] @end <speed ${spd}><${emo} 0.7>${row.text}</></>
```
这一行同时用了 5 种语法，任何人（包括 LLM）都很难一次写对。更根本的问题：
- 表演文本与数据生成逻辑**生命周期不同**（台词由编剧/LLM 改，采样策略由数据工程师改），放在一个文件里互相污染。
- 数据生成真正需要的东西（笛卡尔积、分层采样、配额、去重、切分比例、外部数据源）DSL 永远做不全，最后用户还是会去写 Python；那不如一开始就提供"**声明式 manifest + 任意语言生成 JSONL**"两条路。
- 插值 `${row.text}` 把外部数据原样拼进标记语言 = **注入漏洞**：数据里一个 `[` 或 `<` 就会改变语义（和 SQL/HTML 注入同构）。v0.2 没有转义规则。

### 2.5 "未注册的 `[…]` = 自由表演" 有一个隐蔽的版本化炸弹
今天 `[sing]` 未注册 → 作为自由指令 "sing" 传给 ElevenLabs；明天标准库注册了 `sing`（带音高参数、走唱歌模态）→ **旧脚本含义静默改变**。v0.2 只考虑了拼写错误，没有考虑词表演进。v0.3 的解法：保留开放世界（这是易用性的关键），但用 ①词表版本锁定、②"名字语义稳定"治理规则、③编辑距离警告三件事兜住。

### 2.6 说话人前缀有歧义
`他说：你好` 会被解析成说话人"他说"。中文正文里冒号极其常见。v0.2 没有规则。

### 2.7 中文输入体验未被认真对待
v0.2 的 `[` `<` `@` `#` `$` `{` `/` `\` 在主流中文输入法默认状态下分别变成 `【` `《` `@`(多数不变) `#` `￥` `｛`/`「` `、` `、`。中文作者要么不停切换中英文标点，要么写出解析失败的脚本。而中文剧本里还有大量 `（笑）`、`【重要通知】` 这类约定，需要明确态度。

### 2.8 IR 是封闭的
`ir.Style` 是写死字段的 Go struct（Speed/PitchSt/…/Oral/Dialect）。新增一个能力（比如"气声度 breathiness"、"空间方位"）就要改 IR 类型 → 改所有 provider 编译代码 → 违背"新能力不改核心"。

### 2.9 错误信息与工具友好性
- 多语法 + 自动状态作用域，使得错误位置难以定位（"`</>` 关闭了哪个？"）。
- 没有为 LLM 提供"能力卡片"（当前词表 + 当前 provider 支持度）的生成机制；没有自动修复常见 LLM 错误（`<laugh>`、`(laughs)`、`*laughs*`、`[/slow]`）的规划。

### 2.10 v0.2 做对的（必须保留）
- 意图标签 → IR → **能力声明驱动的降级链**（native-tag → param → ssml → instruction → postprocess → asset → drop）。
- 自由表演指令是一等公民（市场趋势：固定枚举 → 自由文本）。
- 命名空间透传、caps YAML 带 `verified/deprecated`、外部进程插件、manifest 字段、合规元数据、voices.lock。
- 中文别名、渐进式披露的思路。

## 3. 设计方向对比

评分 1–5（5 最好）。"LLM" = LLM 一次写对的概率；"IME" = 中文输入法友好度；"扩展" = 新能力不改语法的程度；"冲突" = 与 provider 原生语法的冲突少。

| 方向 | 代表 | 易学 | LLM | IME | 扩展 | 冲突 | 主要问题 |
|---|---|---|---|---|---|---|---|
| A. XML/SSML 式 | SSML、Azure mstts | 2 | 4 | 1 | 3 | 1 | 冗长、闭合名、`<` 冲突；人类不愿写；厂商扩展碎片化（mstts:/amazon:）——SSML 20 年的教训 |
| B. 纯 JSON/YAML | Hume utterances[]、EL Dialogue inputs[] | 2 | 5 | 2 | 5 | 5 | 不适合"文本中间插一个笑"；可读性差；但**作为 IR/交换格式**极好 |
| C. 嵌入 Go（builder API） | — | 1（对非程序员） | 3 | — | 5 | 5 | 编剧/LLM 不写 Go；应作为**库 API**存在，不作为作者语言 |
| D. Markdown 式 | Speech Markdown `(text)[emphasis]` `[3s]` | 4 | 3 | 3 | 3 | 3 | Speech Markdown 只编译到 SSML、词表封闭、社区小，几乎停止演进；`(text)[x]` 文本在前标签在后，嵌套难读 |
| E. 剧本式 | Fountain、Yarn Spinner `名字: 台词` | 5 | 5 | 4 | 3 | 4 | 只解决"谁说"，不解决"怎么说"；Fountain 用大写区分角色名，中文无大小写 |
| F. 对话语言 | Ink、Yarn Spinner | 3 | 3 | 3 | 4 | 3 | 分支/变量是游戏需求；Yarn 的 `[wave]…[/wave]` 标记和 `<<command>>` 两套语法是同样的复杂度问题 |
| G. 统一函数式标记 | Typst `#f(args)[content]`、BBCode `[b]…[/b]` | 4 | 4 | 3 | 5 | 3 | Typst 的启示：**一种调用形态 + 内容块**就能覆盖全部；BBCode 的闭合 `[/x]` 中 `/` 在中文 IME 下成 `、` |
| H. 自然语言 + 标签 | ElevenLabs v3 `[whispers]`、Fish S2 `[...]`、Inworld | 5 | 5 | 4（`【】`） | 5 | 3 | 词表开放 = 易用；但无参数、无区间、无多人、无精确控制、无版本概念 |
| I. 模板语言 | Jinja、Mustache | 3 | 4 | 2 | 3 | 3 | Jinja 逻辑强 → 不可复现、难审；Mustache "无逻辑"的教训：**模板只做替换，逻辑在数据里** |
| **v0.2（混合）** | — | 2 | 2 | 1 | 4 | 2 | 见 §2 |
| **v0.3 推荐 = E + H + G 的交集，B 做配置/数据/IR，C 做库** | — | 5 | 5 | 5 | 5 | 4 | 见 §4 |

### 关键先例教训
1. **SSML**：表达力足、无人愿意手写；厂商通过私有命名空间扩展，导致"标准"名存实亡。→ 学其**命名空间**，弃其语法。
2. **Speech Markdown**：轻量语法是对的，但"只编译到 SSML + 封闭词表"让它跟不上自由文本时代。→ 词表必须开放、编译目标必须多范式。
3. **ElevenLabs v3 / Fish S2 / Inworld**：`[自然语言]` 已经成为事实标准，LLM 训练数据里海量存在。→ **把我们的唯一语法做成它的超集**：任何合法的 EL v3 文本几乎就是合法的 Timbrex。
4. **Fountain**：纯文本即合法、约定优于标记。→ L0 纯文本可用，剧本行 `名字: 台词`。中文无大小写 → 用"cast 声明"代替大写规则消歧。
5. **Yarn Spinner**：`名字: 台词` + `[markup]` 被大量非程序员接受；但 `<<cmd>>` 第二套语法是负担。→ 只留一套。
6. **Typst**：统一 `函数(参数)[内容]` 让排版与编程合一、扩展无需新语法。→ 一种 tag 形态 `[名 参数|内容]` 覆盖点、状态、区间。
7. **Markdown 代码围栏**：```lang 原样块是所有 LLM 最熟悉的"逃生口"。→ 用于 SSML/原生原文透传。
8. **Mustache**：模板无逻辑 + 默认转义 `{{x}}`、原样 `{{{x}}}`。→ 数据集模板照抄，并直接解决注入问题。
9. **HTML 的宽容解析**：浏览器能修复错误 HTML 是 Web 成功的原因之一，但也带来多年歧义。→ Timbrex 解析**严格且确定**，宽容放在独立的 `timbrex fix`（显式、可审阅的改写）。

## 4. 推导出的 v0.3 设计决策

### 4.1 语言边界：三层分离
| 层 | 载体 | 内容 | 谁写 |
|---|---|---|---|
| 表演文本 | `.tbx` 正文 | 谁说、说什么、怎么说、何时发生 | LLM / 编剧 |
| 配置 | YAML（front-matter 或 `timbrex.yaml`/`cast.yaml`） | 音色/克隆/设计、provider、合规、输出、透传参数 | 工程/制作 |
| 数据生成 | `*.tbxset.yaml`（声明式）或任意语言生成的 `items.jsonl` | 数据源、组合/采样、seed、切分、模板 | 数据工程 |

`.tbx` 正文**没有任何控制流**；数据集模板只有 `{{变量}}` 替换（默认转义）。

### 4.2 一种括号、一条规则
所有标记都是 `[头 参数…]` 或 `[头 参数…|内容]`。`【】` `｜` `：` `“”` 与半角等价。没有 `<>`、没有 `@`、没有 `$`、没有 `#`。
作用域**只由位置决定**，没有配置项：
- 写在台词中间 → 事件发生在此处 / 状态持续到本轮台词结束；
- 带 `|内容` → 只作用于内容；
- 独占一行 → 作用于此后整个场景，直到被同名标签覆盖或 `[reset]`。

### 4.3 开放词表 + 治理
- 未注册的 ASCII `[…]` = 自由表演（保持 EL v3 式的易用）。
- `【…】`（全角）只有在头是已注册名/别名/命名空间时才是标签，否则是普通文本 → `【重要通知】` 安全。全角自由表演写 `【演 带着哭腔】`。
- 词表按包版本锁定（`timbrex.lock`）；新注册名必须满足"**名字语义稳定**"规则（降级到自由文本时与其字面含义一致），否则只能进命名空间。
- `timbrex check` 对与已注册名编辑距离 ≤2 的未知头给出"你是不是想写 [laugh]？"。

### 4.4 开放 IR
IR 节点 = `{Feature string, Args map, Note, Span}`，不再有写死字段的 Style 结构体。新能力 = 新 feature id 字符串，核心代码不变。

### 4.5 能力触达五级（每一级都不改语法）
1. 标准标签（可移植，自动降级）
2. 包标签（社区/用户 YAML 或 Go，可移植，包内定义降级）
3. 命名空间标签 `[ns:名 参数|内容]`（适配器注册，精确控制）
4. 命名空间原文 `[ns:任意原生文本]` 与 `[ns:set 键=值]` 请求参数
5. 原文围栏 ```` ```ssml azure ```` 整块原生

### 4.6 版本化拆成三条独立轴
语法版本（`timbrex: 1`，目标是永不变）、词表包版本（semver，锁定）、能力声明日期（caps `verified`）。这样 provider 每周更新也不会动语法。

## 5. 取舍与风险（诚实说明）

| 取舍 | 我们选择 | 代价 | 缓解 |
|---|---|---|---|
| 区间写法 `[慢|文本]` vs BBCode `[慢]文本[/慢]` | `|` 内联 | 长区间（跨多句）写起来不如 BBCode 自然；LLM 对 BBCode 更熟 | 长区间用"状态标签 + 位置作用域"（本轮/整场）；`timbrex fix` 自动把 `[/x]` 改写；`/` 在中文 IME 下是 `、` 也是选择 `|` 的理由 |
| 开放世界（未知 = 表演） | 保留 | 拼写错误静默成为表演；词表演进可能改变含义 | 锁文件 + 语义稳定规则 + 编辑距离警告 + `--strict-tags` |
| 说话人必须在 cast 声明 | 是 | L1 多一行 `cast: [小林, 老陈]` | `cast: auto` 显式开启自动识别；`timbrex check` 会提示"看起来像说话人" |
| 控制流移出 | 是 | 简单批量也要另写一个 tbxset 文件 | tbxset 足够短（见 v0.3 示例 3）；`timbrex new dataset` 生成骨架 |
| `[…]` 与 EL/Fish/Inworld/Qwen 同形 | 接受 | 读者分不清是不是原生 | 这是有意为之：对这些 provider 几乎零转换；命名空间 `[el:…]` 用于必须原样时 |
| `（笑）` 不自动当表演 | 是 | 习惯中文剧本的人要改写 | `parens: act` 开关 + `timbrex fix --parens` 一次性转换 + lint 提示 |
| 语法冻结 | 是 | 将来某种表达可能"不够优雅" | 一切新东西只能是新标签/新参数/新围栏 info；真正的语法变更走 `timbrex: 2` + `timbrex migrate` |

## 6. 留给用户决定的问题
见 `SPEC.v0.3.md` §15。最关键的三个：区间写法是否同时接受 BBCode `[/x]` 作为别名；自由表演的默认语言（是否自动翻译成 provider 偏好的英文）；`.tbx` 是否允许 front-matter（还是强制独立 `timbrex.yaml`）。

## 附记（v0.3.1 决策，2026-10-20）
用户决定 **DSL 仅用英文 ASCII**（标签、命名空间、参数、关键字、YAML 键、情绪集、标准库），台词等内容可用任何语言。因此上文 §4.2/§4.3 中"`【】｜：“”` 与半角等价""全角【】仅在头已注册时为标签""中文别名"的方案作废，改为：语法只认 ASCII；全角符号与中文标签词由 `timbrex fix` 自动转换为规范英文，`timbrex check` 给出 lint；说话人 ID 为 ASCII 标识符，中文名放在 cast 的 `name:`；自由表演允许任何语言、推荐英文，由 `act_translate` 按 provider 偏好处理。区间写法重新评估后仍为 `[x|content]`：主要理由改为"BBCode 开标签与状态标签同形，会破坏'位置决定作用域'"，输入法不再是决定性因素。详见 `SPEC.v0.3.md`（v0.3.1）§2.4、§3.3–3.5。
